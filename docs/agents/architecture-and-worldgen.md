# Architecture: threading model and worldgen invariants

The threading rules and the other cross-cutting invariants (state byte, edit-path hooks, fluid and gravity, worldgen purity and caches, far LOD). Moved out of AGENTS.md; text unchanged.

## Architecture: threading model (the most important thing to preserve)

Chunk work is split across threads, and OpenGL calls are only legal on the main thread:

1. `ChunkGenerationWorker` runs dedicated background threads that scan positions around each streaming focus (closest first; `World.Focus` is the camera, or every connected player on a server, and the workers round-robin over the foci with one `ChunkScanFrontier` each) and call `ChunkManager.QueueChunk`, which creates the `Chunk` and generates its block data **on that background thread**.
2. Meshing is scheduled by `ChunkMeshScheduler.ProcessDirtyChunks` (behind `ChunkManager.Update`; main thread, per-frame budget `DirtyStartBudget`, default `MaxDirtyChunksPerFrame`) and runs as plain thread-pool work items (`ThreadPool.UnsafeQueueUserWorkItem`): at most `StreamingConfig.MaxConcurrentMeshGenerations` runners are in flight, each draining a shared queue of pending builds. Mesh generation produces CPU-side `ChunkMeshData` only.
3. Completed mesh data lands in `ChunkMeshScheduler`'s `_completedMeshQueue` and is uploaded to the GPU on the **main thread** in `ChunkMeshScheduler.ApplyCompletedMeshes`, sorted closest-first and capped at `MeshUploadBudget` (default `MaxMeshUploadsPerFrame`) per frame.

Rules that follow from this:

- **Never call GL functions (buffer uploads, `Mesh` creation/disposal, pool uploads/frees through `ChunkGeometryPool`, shader use) off the main thread.** Background work must only produce plain data handed over via the concurrent queues.
- A chunk is only meshed when its block data is ready **and all 6 cardinal neighbors exist with ready data** (`ChunkMeshScheduler.HasAllNeighbors`) — meshing reads neighbor blocks for face culling and cross-chunk AO. Breaking this reintroduces holes/seams at chunk borders (see git history). That scheduling check can go stale (the build waits in the pending queue for a free runner and an unload may take a neighbor away meanwhile), so `Chunk.GenerateMeshData` (`ChunkMeshBuilder.GenerateMeshData`) re-resolves the whole 3x3x3 neighborhood once up front and returns `null` when a face neighbor is gone; callers must then re-mark the chunk dirty rather than apply anything. Only the edge/corner neighbors may be absent, and those read as air (they feed light and fluid corner heights only). The same holds for the 3x3 chunk **columns** a build reads (`ChunkManager.ColumnSource`, see "Chunk meshing"): `ChunkMeshScheduler.ProcessDirtyChunks` drops, and `ImmediateRemesh` re-adds once, a chunk whose nine columns are not all `IColumnSource.IsReady` (an all-air chunk, whose build reads no column, is exempt; a fully enclosed one cannot be told apart without its columns and waits too), `ClientChunkStreamer.ApplyColumn` re-dirties the 3x3 chunk columns on arrival, which is what wakes it, and a build that still finds a column missing returns `null` like a vanished neighbor. The worldgen source is always ready, so singleplayer and the server never wait. A mesh build reaches worldgen only through `WorldgenColumnSource` and the seed-hashed pebble, branch-pile and snow emitters, which is why a seed swap still waits for `ChunkManager.DrainMeshWork`.
- Shared state uses `ConcurrentDictionary`/`ConcurrentQueue`; `Chunk.IsBlockDataReady` is `volatile`. Keep new shared state lock-free in the same style. `ChunkManager.Chunks` is a `ChunkMap` (`Chunks/ChunkMap.cs`) wrapping a `ConcurrentDictionary<long, Chunk>` — it is a wrapper, never a `Dictionary` behind a lock, because chunk-gen workers write it and mesh-build pool workers read it.
- Editing a block on a chunk border must also remesh the affected neighbor chunk(s) — block edits use `ChunkManager.ImmediateRemesh` / `MarkDirty`.
- Performance tuning knobs all live in the per-domain config classes under `src/Config/` (per-frame budgets and thread counts in `StreamingConfig`, worldgen knobs in `WorldGenerationConfig`, and so on); change constants there rather than hardcoding budgets elsewhere.
- Animation curves (interpolation, easing, one-shot pulses) belong in `MathUtils`, not inline in gameplay or render code — everything time-driven should be lerped through one of those helpers rather than snapped.

Other invariants:

- World/chunk coordinates: `Chunk.Position` is in chunk units; world pos = chunk pos × `Chunk.Size` (16). Chunks are cubic and stacked vertically too (3D chunk grid, not 2D columns).
- Blocks are `ushort` IDs (shared with items, up to 65,535); `0` is air. Chunk storage is palette-compressed: `Chunk` holds a `volatile ChunkBlocks` (`Chunks/ChunkBlocks.cs`, whose class doc numbers the invariants) in one of three modes fixed per object: **Uniform** (one id, no array: an all-air, all-stone or all-water chunk), **Indexed** (a palette of up to 256 ids plus one index byte per cell) or **Direct** (one `ushort` per cell, only past 256 distinct ids). It keeps the one-writer, lock-free-reader model. The single writer is the generation worker before `IsBlockDataReady` and the main thread after; readers (mesh and light workers) read the volatile reference **once** per use (a mesh build captures each neighbor's storage once, in `MeshScratch.NeighborBlocks`). An in-mode write mutates in place: a new palette entry is stored and the count published before the cell's index is written with `Volatile.Write`, so a reader never sees an index pointing at an unset slot, and palette entries are never changed, removed or duplicated. A mode upgrade (Uniform to Indexed on the first different id, Indexed to Direct on the 257th) is one-way at runtime: `ChunkBlocks.Set` returns a new object and `Chunk.WriteId` publishes it with one volatile swap, so a reader still holding the old object misses only that newest write, the same tolerated race as before (the edit's own remesh wins). Compaction happens only in `ChunkBlocks.FromDense`: the worldgen fill's `Finish`, the restore of an edited (non-compact) snapshot and the save and net codecs' decode. A live chunk's palette may keep stale entries after edits, so `IdSpan` is a conservative superset (fine for sky cover, occlusion shortcuts and id validation, never for exact answers). Snapshots deep-copy (`ChunkBlocks.Clone` on the main thread in `TakeSnapshot`/`CaptureForNetwork`) and a restore never aliases a snapshot: it shares a Uniform storage (immutable), clones a compact one (`IsCompact`, anything a codec decoded) and recompacts any other. Dense work goes through the thread-static `ChunkBlocks.DenseScratch`, whose only callers are `ChunkTerrainFill.GenerateBlockData` (the stamps write into it), `ChunkRestore`, `ChunkSaveCodec.ReadCore` and `ChunkNetCodec.Decode`; it is not reentrant, and no caller may run foreign code (a callback) between filling it and its last read, which is why `ChunkSaveCodec.Write`, whose name callback runs mid-write, decodes into its own array. Everything else about a block comes from `assets/data/blocks/<name>.json` through `ContentRegistry` (see "Content" above), never from a new `switch` on the id. Hot paths read the flat mirrors (`BlockType.IsSolid/Occludes/CastsAO`, `BlockType.Emission`, `BlockType.PassesLightById`) rather than `BlockType.ById[...]`, so keep new per-id flags in that shape. A static class that sizes a per-id table once per process (`TreeGenerator.LeafById`/`CanopyBlockById`, `FallenLogGenerator.FallenLogById`) allocates it in its static constructor behind `BlockTables.RequireLoaded`, which throws when the type is touched before `ContentRegistry.Load`; a later, wider load never resizes the table, so its lookups are length-tolerant (an id past the table reads false) and no worldgen runs under a swapped registry.
- **Per-block state byte**: beside its id storage (`Chunk._blocks`, a `ChunkBlocks`) each chunk has a lazily allocated `volatile byte[]? _state` (null = all zero), read through `Chunk.GetLocalState` / `ChunkManager.GetStateGlobal` / `TryGetCell` and written only by `Chunk.SetBlockRaw` (no remesh, no scheduling — the fluid tick batches those). Six features share it, one per block: a **horizontal facing** (a `facing: "horizontal"` block such as the wall torch or a hollow fallen log: bits 0-1 the facing, rest 0, written by placement through `Placement.TryMount`, or by `FallenLogGenerator.Stamp` into the generated state array), **fluid levels** (`FluidState` decodes it as source `0`, falling `8` or flowing level `1..7`), **stack counts** (a `stackMax` block's 0 = untouched worldgen, 1..`stackMax` an explicit pile), a **multiblock's facing and offset** (`Multiblock.EncodeState`: the facing in bits 0-1, each 0..3 offset's low bit in bits 2-4 and high bit in bits 5-7, so a 2x2x2 reads `facing | dx<<2 | dy<<3 | dz<<4`; written by `Multiblock.Convert` through `SetBlockRaw`), **tree wood** (`WoodState` on a `tree_wood` block: bits 0-3 the thickness code, `FullCube` = 15 being a whole 16 px cell, bits 4-6 the parent direction in `Chunk.CubeFaces` order or `ParentRoot`/`ParentDetached`, bit 7 the shell flag) and **leaves** (`LeafState` on a leaf block: bits 0-2 the hydration, bit 3 the persistent flag) — see `### Trees`. The tree states are written by `TreeGenerator.Stamp` into the generated state array, by `TreeGrowthWriter` and `LeafDecayManager` through `SetBlockRaw`, and by placement, which passes an explicit state to `PlaceBlockAt` (`BlockPlacer.PlaceBlockAtFace` gives a placed log `WoodState.Detached` and a placed leaf a persistent `LeafState`). Which meaning a byte carries is decided entirely by the block id that owns the cell, so a new user must pick a block kind, never a spare bit. **Every write that is not one of those zeroes it** (`RemoveBlockAt`, `ClearBlockAt` and `PlaceBlockAt` with its default state `0` — which also treats a fluid cell as replaceable), and `Multiblock.Revert` likewise writes its source block with an explicit `0`, so a stale level, count, offset, thickness or hydration can never outlive the block that owned it. Meshing gets it as a second padded snapshot from `ChunkMeshBuilder.FillPaddedSnapshot(padded, paddedState, blocks, neighborStates)`, filled from the neighborhood `ChunkMeshBuilder.TryResolveNeighbors` resolved for the build; the fluid simulation must read cells through `TryGetCell`/`ChunkAt`, never `GetBlockGlobal`, which reports unloaded chunks as air. A seventh meaning belongs to the **openable** blocks (an `open` object in their JSON: the trapdoor, and both halves of a door, which always carry the same byte): `DoorState`, the facing in bits 0-1 like any facing block plus `DoorState.OpenBit` (bit 2), the rest zero; placement writes it closed, and the right-click toggle (`BlockInteractions.TryToggleOpenable`, through `ToggleOpenCell`) flips the bit alone through `Chunk.SetStateAt`. The mesher and `BlockShape` index a facing block's pre-turned models and boxes with `BlockType.ShapeIndex(state, count)` (`state & (count - 1)`), so four-shape blocks keep reading the facing and an openable block's eight read the open bit too.
- **Station block entities**: `CampfireManager`, `QuernManager`, `KilnManager` and `CastingManager` are all owned by `World`, all **main thread only**. A lit campfire, a spinning quern, a kiln's fuel and crucible and a mold's cast progress are saved in `stations.json` (see "Saves"): each manager has a `Capture()` and a `Restore(...)` over `StationSaveData` (content by `SaveNames` name, never numeric id), `WorldPersistence` restores them at construction and writes them on every autosave and flush, and **a new station registry must add its own pair and list**. Each is keyed by the cell (the kiln by its structure's anchor), each is ticked from `World.Update` and each has a `NotifyBlockRemoved` that `BlockEditor.RemoveBlock` calls so a broken station drops what it held. `AmbientEffects` gathers every burning cell once a frame (campfires and lit kilns in every update, plus goblin torches in the full `World.Update`; a client's `UpdateClient` gathers the stations only) and `World.FireCells` exposes the list, which feeds both the fire billboards (`FireParticleSystem.SpawnOffset`) and the warm point lights (`FrameLighting.FireLightOffset`, which `RenderManager` still forwards for the tests), so a new fire source only has to appear in that list. Their render passes — `StationPasses.RenderQuerns`, `RenderKilns`, `RenderCastings` — sit inside the existing `entityPass` profiler span rather than adding sections of their own. On a multiplayer server they tick in the server's `World.Update` and a pour is bound to the pouring player (`CastState.PourSource`, its `PlayerContext`, which pauses once the player left); a client never ticks them: its managers are display-only mirrors replaced by the server's `StationState` snapshot (each manager's `WriteNet`/`ReadNet`, `StationNetCodec`), and only a quern top keeps turning between snapshots (`QuernManager.Animate`).
- **Fluid tick**: `Simulation/Fluids/FluidManager.cs` (owned by `World`, main thread only) is a *scheduled-cell* simulation, not a scan. `World.Update` calls it once per frame after `BlockEditor.UpdateToppling`; it runs whole ticks every `SimulationConfig.FluidTickSeconds` (0.25 s), at most `MaxFluidTicksPerFrame` of them per frame, and drops the leftover time so a hitch never leaves it spiraling. Each tick takes the set of cells scheduled by the previous one (packed as `long`, 21 bits per axis, through `CellKey` (`src/Chunks/CellKey.cs`), which forwards to the one bit math in `ChunkKey` (`src/Chunks/ChunkKey.cs`), the packer of a **chunk** position for `ChunkMap` and for `ChunkManager`'s dirty/queued/generating/placement dictionaries; `CellKey`'s keys are block-scale, `ChunkKey`'s are chunk-scale, and neither floors nor truncates differently from `VoxelCoords.ChunkPosOf`), recomputes every **non-source** fluid cell from its neighbors (Minecraft's `getNewLiquid`: two adjacent sources over ground that cannot drain become a source themselves, fluid directly above means falling, otherwise one level thinner than the fullest neighbor, and nothing left means the cell drains to air), then spreads it downwards, or sideways toward the nearest hole within `FluidSlopeSearchDistance` (ties spread evenly). The level rules are per-fluid data (`flow.*` on the block: lava updates every other tick, spreads 3 instead of 7 and never forms new sources). Contact hardening runs before all of it: a fluid cell touching its `hardensTouching` fluid becomes `hardensTo` (lava beside water becomes cobblestone), and a flow settling against a fluid that hardens on its touch crusts over the same way, so water reaching lava also yields cobblestone whichever side ticks first. Spreading only ever writes into non-fluid `IsReplaceable` cells, popping the fragile block it washes away through `DropManager.SpawnLoot`; a cell that already holds fluid recomputes itself on its own tick. Writes go through `Chunk.SetBlockRaw` and dirty only the cell's own chunk plus the face-adjacent chunk on each axis where the cell sits on a border, batched into `MarkDirty` (`FluidCells` over its own `ChunkCellCache`) at the end of the tick — not `ImmediateRemesh`, and never `MarkAreaDirty`, because a fluid passes light and casts no AO. A cell reschedules itself and its neighborhood exactly when it changed or wrote into a neighbor, so settled water costs nothing.
- **Waking worldgen water**: the sea is generated as static source cells, so a cave or entrance carved into a land column beside it would leave a wall of water standing against worldgen air that nothing ever schedules. `FluidManager.WakeLoadedChunks(chunks)` — called from `World.Update` each frame, immediately before the fluid tick — fixes that by scheduling the frontier of its water against a carved cavity when it loads, so the sea pours into whatever breached it exactly like Minecraft water does when you dig into an ocean. Only cells at or below their column's natural terrain top count (`FluidWakeRules.IsCarvedFlowTarget`), so open air above the terrain — a ravine, a beach, a hillside — is never woken and generated water stays static across it. It has two halves: the **interior**, collected on the generation worker at the end of `ChunkTerrainFill.GenerateBlockData` into `Chunk.FluidFrontier` through `FluidWakeRules.IsWakeTarget` (local block indices of every fluid cell with a `FluidWakeRules.IsCarvedFlowTarget` neighbor in -X/+X/-Z/+Z/-Y — never +Y, since water does not flow upward and every sea-surface cell has air above it; only its own `_blocks` are read, so worldgen stays a pure per-chunk function), and the **borders**, which need both chunks loaded and are therefore scanned on the main thread (`FluidWakeScanner.WakeBorders`) over the shared 16x16 plane of each face neighbor, scheduling whichever side holds the fluid when the other side is a carved cavity (the vertical faces only ever schedule the fluid above the hole). Chunks entirely above every level they could share with a neighbor (`ColumnData.MaxWaterLevel`, never below `SeaLevel`) skip the border scan — generated water cannot reach them, and player-placed water is woken by the edit paths. The queue of newly generated chunks is `ChunkManager.TryDequeueLoaded`; a consumer must re-check that the chunk is still the live one at its position, because an unload can race the queue. Once the frontier has settled, it costs nothing again. Deep lava pockets wake through the same path: the frontier scan is fluid-generic, and chunks at or below `LavaMaxY` report theirs even when they never held sea water.
- **Every block edit path must call `FluidManager.ScheduleAround(cell)`** (or `ScheduleBox(min, max)` for a batch) or the water beside the edit will never notice it: `BlockEditor.RemoveBlock`, `BlockEditor.FellWood` (per cleared cell, and in both single-block branches), `BlockPlacer.PlaceBlockAtFace` (which every placement ends in: `BlockPlacer.TryPlaceBlockFromRaycast` through `PlaceAgainstFace`, and the item-use `IItemUseWorld.PlaceBlockAtFace`), `BlockInteractions.ToggleOpenCell`, `TntManager.Detonate` (`ScheduleBox` over the blast box grown by one; the blast also **skips fluid cells**, since a dry crater under water would just refill from every side) and bucket edits through `FluidManager.SetCellImmediate` (`WorldItemUse`'s `ScoopFluidCell`/`PourFluidCell`), which is the only fluid write that remeshes synchronously. Mining never takes a fluid out: `BlockEditor.RemoveBlock` returns early on `BlockType.IsFluid`, so only a bucket removes fluids.
- **Every block edit path must also call `LeafDecayManager.ScheduleAround(cell)`** (or `ScheduleBox(min, max)` for a batch) or the leaves near the edit never re-derive their hydration: a cut limb's canopy would hang forever, and an orphaned wood cell would never crumble. `Simulation/LeafDecay/LeafDecayManager.cs` (owned by `World` as `_leafDecay`, main thread only) grows each scheduled box by its `ScheduleReach` itself, so a caller passes only the edited cells. The current call sites: `BlockEditor.RemoveBlock`; `BlockEditor.FellWood` (`ScheduleAround` in both single-block branches, one `ScheduleBox` over the whole felled batch, never one per cell); `BlockPlacer.PlaceBlockAtFace`, which every placement goes through (`BlockPlacer.TryPlaceBlockFromRaycast` and the item-use `IItemUseWorld.PlaceBlockAtFace`); the `IItemUseWorld` bucket and TNT-prime wrappers on `WorldItemUse` (`ScoopFluidCell`, `PourFluidCell`, `RemoveCellForPrime`), scheduled for uniformity; `BlockInteractions.ToggleOpenCell`; `TntManager.Detonate` (`ScheduleBox` over the blast box); and `TreeGrowthWriter` (one `ScheduleBox` over the box it wrote). A new edit path adds its call next to its `FluidManager.ScheduleAround`.
- **Unbreakable blocks** (`unbreakable` in the block schema) are refused by the semantic writers (`Chunk.RemoveBlockAt`, `ClearBlockAt`, `Placement.CanOccupy`) and the gameplay entry points, never by `Chunk.SetBlockRaw`, so a new raw-write path must guard itself. The one sanctioned write over one is `Chunk.CollapseWriteAt` (the tower's doors and piles, and BT-8's collapse; both through `TowerBlockWriter.TryReplace`, which also spills a replaced chest through `ChestManager.NotifyBlockRemoved`), which runs no hook: its caller owes every hook in these bullets (fluid and leaf-decay schedules, the falling-block topple, the far-LOD and canopy hooks, `UnmarkPlayerPlaced`) and the remesh.
- **Gravity**: `Simulation/FallingBlockManager.cs` (owned by `World`, main thread only) topples `falls` blocks into `FallingBlock` entities and writes rested cubes back as blocks. Every edit path that can unsupport one must call `TryTopple` above it (`BlockEditor.RemoveBlock`, `BlockEditor.FellWood` per cleared cell, `BlockPlacer.PlaceAgainstFace` at the placed cell (the path of `BlockPlacer.TryPlaceBlockFromRaycast`) and `WorldItemUse`'s `IItemUseWorld.AfterPlaced` after an item's own placement, `TntManager.Detonate` via `CheckColumn` bottom-up over the blast box); fluids never count as support, so fluid edits need no hook. A landing cube slides with chance (8 - solid neighbors of its support) / 8 toward a random clear side, corners included (a corner needs its two flanking sides and the three cells above it clear), committing to its direction across landings, and drops straight once past the edge. Sand stacks on sand: a falls-block support never slides, so towers rebuild. A calm landing converts at once so a collapsing tower settles bottom-up instead of interpenetrating, and a cube that would rest over air pops out as a drop instead of floating. A live cube owns its cell: `BlockPlacer.PlaceBlockAtFace` refuses placements into one, cubes shove the player aside one-way (`Camera.PushOutOf`, never through walls, never while flying), and a cube motionless-but-unsettled for 5 s breaks into its usual loot instead of hovering. Shorelines generate from sand (`TerrainGenerator.IsBeachHeight`, gravel-capped where `IsGravelPatch`); the far LOD wears sand and gravel there too, the gravel read with one noise eval per cell.
- **TNT**: `Simulation/TntManager.cs` (owned by `World`, main thread only, never ticked on a client) runs the primed cubes (`PrimedTnt`). A cube lit by hand burns `TntManager.PlayerFuseSeconds` (1 s) and one lit by another blast `ChainFuseSeconds` (0.5 s), so a chain stays prompt; `PrimedTnt.WhiteFlash` ramps its strobe from 4 to 16 Hz over whatever fuse it was given (`FirestarterTests`). A blast shoves everything loose within `BlastRadius` away from its center (`BlastImpulse.At`: `BlastPushMaxSpeed` at the center falling linearly to zero at the radius, the direction tipped up by `BlastPushUpBias`, never growing with distance): at the end of `Detonate`'s clearing, before the falling-block sweep (so sand the blast undermines falls straight), the other primed TNT (`PrimedTnt.Push`, chained cubes at spawn), the drops (`DropManager.ApplyBlastImpulse`, the blast's own loot included) and the falling cubes in the air (`FallingBlock.Push`); then `MobDirector.PushFromBlast` (World's mob component, called once per blast from `World.Update`) takes each center `TntManager.Blasts` reports and shoves the living mobs (`Mob.Shove`, sideways) and the players through `IMobTarget.TakeHit` with no damage: the local camera's knockback in singleplayer, each `ServerPlayer`'s queued knockback on a server (its `PlayerStatus` carries it to the client); a creative, flying or dead player is immune. Gameplay, so a client, which never ticks TNT, pushes nothing (`BlastEffectTests`).
- Worldgen must stay deterministic and thread-safe (`FastNoiseLite.GetNoise` is read-only after setup; noise instances are configured once in static constructors and never re-tuned per call). All noise seeds derive from `WorldGenerationConfig.Seed` plus fixed per-channel offsets (`TerrainNoise.MakeNoise`, forwarded as `TerrainGenerator.MakeNoise`; every 2D channel is built by `TerrainNoise.Reseed`); `Seed` reads `WorldSeed.Value`, which `WorldSeed.Apply` sets (rebuilding every noise from it) before a World is built, never while one is live (see "Saves"). Before player edits, terrain obeys:
  - **Nothing generated is ever solid above `height(x,z)`** — heights come from `ColumnCache.Get(...).Heights` (or the `ColumnCache.GetHeights` wrapper) and already include ravines, which are cut into the heightmap so the far LOD sees them too. The ravine cut fades out across the shore band (`OceanShoreWeight`..0.5), so it never slices the ocean's edge; the block at `height` is solid unless a cave or entrance carved it.
  - Both carvers only ever **remove** blocks: `ChunkTerrainFill.GenerateBlockData` fills the columns (grass at depth 0, dirt down to `DirtDepth`, stone below), then `NoiseCaves.Carve` and `WormCarver.Carve` clear air out of the result and `_solidCount` is recounted.
  - **Water** fills every air cell up to the column's own level in a **wet** column, in `ChunkTerrainFill.FillWater` after both carvers and before trees and pebbles: an ocean floor, or a lake or river bed, where a hashed lake bowl or a warped river ridge channel carves the ground below it. There is **no single water plane**: `ColumnData.WaterLevel` (`TerrainGenerator.WaterLevelAt`) is sea level for the ocean, a river's own level for a river (sea level, except on the ramp of an elevated great lake, below), but a lake's **own** surface, so a pond rests in the ground it was dug into instead of at the bottom of a crater dug to sea level. A lake takes that surface from its own rim (`WaterBodies.TryLakeSite`, whose verdict is cached per lake cell, `WaterBodies.PondSiteAt`): the lowest ground on the rim minus `LakeBankDepth`, and a candidate whose rim climbs more than `LakeSiteFlatness` is dropped rather than dug into a hillside, which is what keeps every bank it floods against above the water. A candidate standing above `SeaLevel` is also dropped when a river channel crosses its footprint (`WaterBodies.RiverCrossesSite`, sampled every few blocks across the disc), because the rim is read from `LandHeight` before any river cut and the channel would carve a bank below the pond's surface (rule test `LakeTests.NoRiverChannelCrossesAnElevatedPond`). Its radius (skewed small by `LakeRadiusSkew`), depth and outline (wobbled by `TerrainNoise.LakeShapeNoise`, so a shoreline is ragged rather than a circle) all vary per lake. A second, much rarer **great lake** tier (`WorldGen/GreatLakes.cs`, BIOMEGEN §13 phase D) sits beside the ponds: one hashed candidate per `GreatLakeCellBlocks` cell, a union of one to three lobe discs of radius `GreatLakeMinRadius..MaxRadius` wobbled inward by `TerrainNoise.GreatLakeShapeNoise`, optionally with an island in its main lobe. Its verdict is cached per cell (`GreatLakes.SiteAt`/`BuildSite`): the surface is the lowest ground of a dense walk over each lobe's dry shore annulus minus `GreatLakeBankDepth`, a rim spread over `GreatLakeSiteFlatness`, any ocean or desert weight or a biome that holds no water on the rim or in a coarse interior pass, interior ground rising more than `GreatLakeInteriorRiseMax` over the rim, or any massif or lone-peak disc meeting a lobe refuses the site, and the shore ramp widens with the rim spread. A great lake never refuses a river: a cutting river anywhere in a lobe's shore annulus makes it **river-fed**. A lake standing above `SeaLevel` may carry a **river ramp** (`GreatLakeSite.RampLength`, `(Surface - SeaLevel) * GreatLakeRiverRunBlocks`): past its lobe edges the per-column river level (`GreatLakes.RiverLevelAt`) steps down one block every `GreatLakeRiverRunBlocks` from the lake's surface to `SeaLevel`, never rising away from the lake and never more than a block between neighbors, so a river reaching it meets it at its own surface; the ramp is kept only when it fits (at most `GreatLakeRampMaxLength`, its footprint within the lowest-hash spacing, out of the spawn clearing) and every river sample on it stands in lake-holding ground `GreatLakeRiverBankRise` over its level. A ramped lake may also get an **outflow**: a straight channel `GreatLakeOutflowHalfWidth` wide leaving radially from the lowest eligible point of its rim, running down the same ramp and tapering shut (`GreatLakeOutflowTaperBlocks`) inside it, kept only when its corridor holds for at least `GreatLakeOutflowMinLength`. A river-fed lake keeps its ramp and its own surface; a rim-fed one keeps a ramp only to carry an outflow; a river-fed lake whose ramp cannot be kept falls back to resting at `SeaLevel`, refused when its rim-chosen surface lies below `SeaLevel` or more than `GreatLakeRiverFedMaxDrop` above it. `WaterBodies.SampleSurfaceWater` is the one place the tiers compose, read by `WaterLevelAt`, `SurfaceWaterWeight` and `Compute`: it hands out the river level (the river carve targets `riverLevel - RiverBedDepth`, its lowland fade measured above that level, and `WaterLevelFor` stores it), folds the outflow into the river weight, and wherever the great-lake weight is above 0 it replaces the pond fields, and the river is scaled by `GreatLakes.RiverShare`, exactly 0 wherever lake water stands. `Compute` raises a column left dry under the highest level a ramp neighbor can hold to that level when `GreatLakes.RampRiverBeside` finds ramp river or outflow beside it (it only raises dry ground, so it never opens a leak), and its ravine guard stays at 1 to `RampLength + 1` past a lobe. A pond yields to a great lake at site level (`TryLakeSite` refuses a candidate `GreatLakes.NearAnyFootprint` finds within `GreatLakePondClearance` of a lobe grown by the guard, or by `GreatLakes.RiverReach` for a ramped lake), so no column belongs to both; and `Compute` feeds the great lake's ravine guard (1 inside a lobe, easing to 0 `GreatLakeRavineGuardBlocks` past it) times `WaterBodyThreshold` into `RavineCutFade`, so a ravine tapers in across the guard band and never cuts a bank or an island. Every great-lake output is exactly 0 (the river level `SeaLevel`) outside the accepted lobe discs grown by the guard (by `RiverReach` for a ramped lake) and within `GreatLakeSpawnClearRadius` (= `ReliefSpawnClearStart`), so land elsewhere is bit-identical but for ponds that yield within pond reach of a lake (`GreatLakeSiteTests`, `GreatLakeTests`, `GreatLakeRiverTests`, `LodReliefTests.TheFarLodSitsInsideTheChunkTerrainOverAGreatLake`). `TerrainGenerator.IsWaterColumn` is now just `height < WaterLevelAt(x, z)`, so the carve in `Compute` and the fill agree by construction, and the far LOD draws its sheet at the same per-cell level. Wetness reads the column's `ColumnData.Bed` — the profile before a ravine cut it — not the ravine-cut `Heights`, so a ravine that merely deepens an otherwise dry column holds no water instead of flooding as a narrow spike, while a ravine under a real lake or river just deepens that body (and the cut fades out across the shore band, so no ravine ever cuts the ocean floor). Every other below-level basin is left **dry** — the forest is not flooded wholesale now that ocean carries the bulk of the water — and a desert stays dry; sand and gravel ring actual water only (`TerrainGenerator.SurfaceWaterWeight` gates the height band), never a dry ravine floor in the band. Both the carve and the flood test are scaled by `TerrainGenerator.SurfaceWaterGate` (`WaterDesertFadeStart`/`WaterDesertFadeEnd`), which fades the body out over the last stretch before the desert, so a pond closes on its own forest rim instead of ending in a vertical wall where the hard forest/desert classification flips, while lakes away from a desert keep their full depth. Sea-floor caves still flood, nothing grows in water (wet columns top out in dirt instead of grass), and `IsSubmerged(height)` is only the waterline height test, since wetness is a per-column level now. Generated water is always a **source** (state `0`). A cold column's top water cell is then replaced by `ice` in `SnowGenerator.StampGround` wherever `SnowGenerator.IsFrozenWater` says so (see Biomes), so a cold ocean or lake freezes into a walkable sheet whose edge breaks into floes and open leads over the pack-ice band. `WaterEnabled = false` turns the water off; `LakesAndRiversEnabled = false` leaves oceans only.
  - **Lava pockets** pond over dry cave floors at/below `LavaMaxY` (`LavaGenerator.Stamp`, after the sea so flooded caves stay water): one or two spaced 3D source candidates per group, buried under the terrain so ravines and entrances stay dry. Generated lava is likewise all sources; set `LavaEnabled = false` to turn it off.
  - **The barrier band** (`BarrierGenerator`, see "The barrier") is the one stamp that writes into carved air and fluids: inside its core every cell becomes barrier. It runs after every other stamp, so a later feature can never reopen it; its ramps replace solid, occluding ground only. `BarrierEnabled = false` turns it off.
  - **Battle towers** (`TowerPlacement`/`TowerGenerator`, plans/BATTLE_TOWER.md) write every cell of their disc from the foundation to the roof, as air or block, so they clear the terrain and trees inside. `Stage.Towers` runs right after `Foliage` (so no heightmap-reading scatter floats inside an interior) and before the sky layers; `TowerPlacement.TopReaching` raises the chunk's `maxHeight` where a tower reaches it, so a tower chunk takes neither the empty early-out nor the sky short path, and `FeatureReachChunks` folds in the tower reach. A chunk off every footprint pays only the cell hashes and box rejects. Surface ruins and their waystone satellites keep off tower footprints (`RuinPlacement.TrySurfaceGround` asks `TowerPlacement.Meets`; towers never read ruins). `TowersEnabled = false` turns them off.
  - **Solid clouds** (`CloudPatchGenerator`, see "Solid clouds") only replace air inside `CloudSlabBottomY..CloudSlabTopY`, the **cloud sea** (`CloudSeaGenerator`) inside `CloudSeaBottomY..CloudSeaTopY` and the **sky islands** (`SkyIslandGenerator`, see "Sky islands", with their flora and the sky trees, see "Sky biomes") inside `SkyIslandBottomY..SkyIslandTopY`; the three bands are disjoint and each is a pure function of (x, z) and the seed. A chunk entirely above the terrain and any water normally takes the empty early-out, so a sky chunk outside the three bands stays empty and never meshes; one whose floor lies in any of their `WriteBand`s instead takes a short path (`ChunkTerrainFill.StampSky`: the gated stamps, `Stage.Clouds`, `CloudSea`, `SkyIslands`, `SkyTrees`, then the solid recount, so it is non-empty and meshes), which `StampGateTests` proves identical to the whole pipeline (`stampGates: false`). `CloudPatchesEnabled`, `SkyIslandConfig.CloudSeaEnabled` and `SkyIslandsEnabled` turn them off.
  - **Hell** (`HellGenerator`, see "Hell") owns every cell at or below `HellTopY`: its stamp, run after the barrier (`Stage.Hell`), overwrites them all whatever the overworld pipeline put there, and its `WriteBand` is open-ended downward (`int.MinValue..HellTopY`). A chunk wholly in hell (`HellGenerator.Covers`) therefore skips the neighborhood scan, the carvers and every other stamp and only runs the hell stamp, the vulcanite veins over its basalt (`VulcaniteGenerator.Stamp`, `Stage.Vulcanite`, also run after the hell stamp on the overworld path, where it veins the barrier band too), the hell trees (`HellTrees.Stamp`, also run after the hell stamp on the straddling chunk), the solid recount and the frontier scan, which is bit-identical (`StampGateTests` proves it: the ungated `stampGates: false` path runs the whole pipeline there) and about 0.26 ms a chunk warm. Chunks load to any depth (the streaming sphere has no vertical cap); overworld cave slimes never spawn in hell (`MobSpawner.TryFindCaveSpawn`). `HellEnabled = false` turns it off and leaves stone.
  - Caves fade out within ~`CaveSurfaceFadeEnd` blocks of the surface (`WormSurfaceMargin` for worms), except inside entrance zones — sparse patches where `ColumnData.EntranceWeight` lifts the fade and caves reach the sky. The entrance weight fades out before the shore band (`EntranceShoreFade`, see `OceanShoreWeight`), so a cave never breaches a beach or the sea floor into a water-filled hole.
  - Worldgen is a **pure function of world position**: each chunk generates its own blocks with no cross-chunk writes, so neighbors agree at their borders without shared state. Worm paths are cached per 64-block XZ cell in `WormCarver` exactly the way column data is cached per chunk column in `ColumnCache.Get`, and so are the four tree caches in `TreeBatches` and `TreeCanopy` (see `### Trees`): the cell batches (`TreeBatches.BatchCache`, every tree rooted in one 64x64 XZ cell grown together, shared by `Stamp` on the generation workers and the first LOD ring's canopy on the LOD builder), the solo tree shapes (`TreeBatches.ShapeCache`, which `BuildBatch` reads as the neighboring cells' obstacles), the grown canopy tops (`TreeCanopy.CanopyCache`) and the far rings' crown-proxy canopy (`TreeCanopy.ProxyCanopyCache`), the last two read by their one engine caller `LodRegion.BuildMeshData` once per *fine* column of a region; and so are the massif and lone-peak site verdicts (`TerrainPeaks.MassifSiteAt`/`PeakSiteAt`, one accepted-or-rejected `TerrainSite` per site cell) and the great-lake verdicts (`GreatLakes.SiteAt`, one `GreatLakeSite` per great-lake cell, whose factory reads the massif and lone-peak caches one way: a lake reads the peaks, the peaks never read lakes, so nothing recurses); and so are the pond verdicts (`WaterBodies.PondSiteAt`, one (accepted, surface, floor) per lake cell, whose factory reads only heights, river weights and the great-lake footprints, never a water level, so it cannot recurse either); and so are the hell trees (`HellTrees`, one grown tree or none per hell tree cell and layer, whose factory reads only hell's own pure field); and so are the sky trees (`SkyTrees`, one grown tree or none per sky tree cell, whose factory reads only the sky islands' own pure column rule); and so are the tower sites (`TowerPlacement`, one accepted `TowerSite` or none per 1536-block tower cell, whose factory reads only heights, biomes, water and the structure templates, never a ruin). All thirteen go through `GenerationalCache<TKey, TValue>` (`WorldGen/GenerationalCache.cs`): the cache is split into G generation dictionaries published as one immutable node swapped by `Interlocked.CompareExchange`, a read probes the newest first, a miss computes into the newest, and when the newest fills its `capacity / G` insert budget the node rotates and the *oldest* generation is dropped — so eviction retains the most recently used generations instead of clearing wholesale, and an entry read while it sits in the oldest generation is promoted forward (a second chance). Entries are deterministic, so a race, an eviction or a duplicate yields identical values, and the worst an evicted entry can ever cost is a recompute. Capacities and generation counts all live in `WorldGenerationConfig`, one pair per site: `ColumnCacheCapacity`/`ColumnCacheGenerations`, `CellCacheCapacity`/`CellCacheGenerations`, `TreeBatchCacheCapacity`/`TreeBatchCacheGenerations`, `TreeShapeCacheCapacity`/`TreeShapeCacheGenerations`, `TreeCanopyCacheCapacity`/`TreeCanopyCacheGenerations`, `TreeProxyCanopyCacheCapacity`/`TreeProxyCanopyCacheGenerations`, `MassifSiteCacheCapacity`/`MassifSiteCacheGenerations`, `PeakSiteCacheCapacity`/`PeakSiteCacheGenerations`, `GreatLakeSiteCacheCapacity`/`GreatLakeSiteCacheGenerations`, `PondSiteCacheCapacity`/`PondSiteCacheGenerations`, `HellTreeCacheCapacity`/`HellTreeCacheGenerations`, `SkyTreeCacheCapacity`/`SkyTreeCacheGenerations` and `TowerSiteCacheCapacity`/`TowerSiteCacheGenerations` — every site ships at 4 generations, and that count is a re-pricing lever that may only be moved against a real capture, never blind. The factory a site passes to `GetOrAdd` must be a `static`, non-capturing delegate *field* (`ColumnCache.Compute`, `WormCarver.BuildCellFor`, `TreeBatches.BuildShapeFor`, `BuildBatchFor`, `TreeCanopy.BuildCanopyFor`, `BuildProxyCanopyFor`, `TerrainPeaks.BuildMassifSiteFor`, `BuildPeakSiteFor`, `GreatLakes.BuildSiteFor`, `WaterBodies.BuildPondSiteFor`, `HellTrees.BuildFor`, `SkyTrees.BuildFor`, `TowerPlacement.BuildFor`), because the factory takes the key alone: a lambda written at the call site that captured locals would allocate a closure on every call, hits included, on the generation workers — recomputing those values from the key on a miss is the cheaper trade. **Standing rule: only values that are a pure function of the key may live in that type.** State carrying *player edits* must never be moved into it, because there eviction is data loss rather than a recompute — `LodColumnCaps` (mined-column LOD caps) and `TreeCanopy.CanopyDisturbed` (felled-canopy markers) are the two current examples, and both are tracked as their own items rather than converted. They are still plain process-global tables; `LodEditState` exports and imports them per world (with the `LodSurface` overrides) and `WorldSeed.Apply` resets them between worlds.
  - 3D cave noise is sampled on a `CaveNoiseStride` lattice (aligned to world coordinates so adjacent chunks share boundary samples) and trilinearly interpolated per block before thresholding. Ore veins (`MalachiteGenerator`, `CoalGenerator`, `HematiteGenerator`) and gravel/sand pockets (`GravelPocketGenerator`) are sampled the same way on the `OreNoiseStride` lattice through `OreNoiseLattice` (PERF_TODO G3): a lattice cell whose 8 corners are all at or below the threshold holds none (a trilinear blend never exceeds its largest corner, so this is part of the field, not an approximation), and `HasOre`/`HasPocket` evaluate the very same field (`OreNoiseLattice.Exceeds`), so a point query equals what the chunk stamp writes, bit for bit and across chunk seams (`OreNoiseLatticeTests`). `HematiteGenerator.HasOre` applies the same world-Y ceiling (`HematiteMaxY`) as its stamp's host rule, which is what keeps that equality for an ore confined to a depth band (`ChunkTerrainFill` also skips the call for a chunk whose floor is above the ceiling, which is bit-identical). A rule may shift the threshold per cell (`IOreLatticeRule.ThresholdShift`, the cave biome richness, `CaveRichness`): the stamp culls a lattice cell against the threshold plus the rule's lowest shift (`MinThresholdShift`) and tests each host cell with `max > t` and `blend > t` for its own `t = threshold + shift`, exactly what the point query tests when passed that sum, and a shift of 0 is the plain field bit for bit (`CaveOreRichnessTests`). `NoiseCaves` has twelve lattice channels: the original eight fields, the sub-biome shape scale (offset 182, sampled only with a sub-biome), intermediate pockets (offset 187), and two elongated desert tunnel samples (only with DesertEcho). Plain and frozen echo use regular carving; desert uses separate tunnels and bounded large rooms (`CaveShapeTests`). The cave biome map (`CaveBiomeMap`) is classified once per chunk, right after the column fill, and handed to the carvers, the ores and the palette pass.
- **Far-terrain LOD**: full-detail chunks load to `ChunkRadius` (16 chunks = 256 blocks); a cascade of LOD rings defined in `LodRegion.Levels` extends the render distance (level 1: 2-block cells to 512, level 2: 4-block cells to 1024, level 3: 8-block cells to 2048 blocks). Regions are columns meshed at reduced resolution straight from the heightmap cache (`LodRegion.BuildMeshData`, built by `LodMeshBuilder` and `LodFaceEmitter`) (no block data; a column a server's world source supplies is read from that source's `ColumnData` instead, see "World sources"). Each level's heights are eroded (min over a widened fine-column window) and biased downward so its mesh sits strictly inside real terrain *and* strictly below the next finer level — finer geometry always buries coarser via the depth buffer, so no masking or camera-driven remeshing exists. Because those shells are stacked, only one level may actually be drawn per area — otherwise they are all visible once the camera is inside the terrain — so `LodCoverPass.UpdateBuriedFlags` marks each region whose footprint is fully covered by *loaded* finer-level regions (region grids nest exactly: one region = ratio×ratio regions of the finer level) and `TerrainPasses.RenderLod` skips those. Testing loaded regions rather than each level's radius means an unbuilt finer region can never open a hole in the horizon. The LodGen claim scan (`LodRegionClaims.FindClosestNeededRegion`) merges the levels by each region's nearest-point distance to the camera (`NearestDistanceSq`, the finer level first at equal distance): in the steady state that is still finest-first, and after a long teleport the regions under the camera on every level come first, so a coarse shell left from the old ring is buried by its finer children within a few builds instead of after the whole finest ring (`LodManagerTests.TheScanReplacesTheCoarseShellUnderTheCameraBeforeFillingTheFinestRing`). The finest level (0) has no finer level to hide it, so it is additionally marked buried wherever the full-detail chunks its shell could show through are loaded *and* meshed (`LodCoverPass.IsCoveredByChunks`, using the per-column inclusive chunk-Y ranges recorded at region build in `LodRegion.ColumnCyMin/ColumnCyMax` and `Chunk.IsMeshed`, which unlike `HasMesh` is true for all-air and fully enclosed chunks too). This is needed because caves cut into the band the shell occupies and would otherwise show it from inside; presence is tested per chunk rather than by horizontal distance because the load volume is a sphere. LOD side faces use grass at the top cell, dirt above `NominalDirtDepth` and the stone tile below it, so far cliffs match near ones; a desert cell wears sand over sandstone and a sea-floor cell the sand/gravel/stone band its depth picks (`LodRegion.BuildMeshData` reads `ColumnCache.GetBiomes`). The nesting invariants (`SampleMargin(L+1) >= SampleMargin(L) + CellSize(L) - 1`, `HeightBias(L+1) >= HeightBias(L) + CellSize(L)`) must hold when adding levels, and `Camera.NearPlane`/`FarPlane` are tuned to keep those separations from z-fighting at the outermost ring. LOD draws before chunks, coarsest level first (`TerrainPasses.RenderLod`). Destroying a block would expose the buried LOD, so removals cap that column's LOD height below the removed block (`LodColumnCaps.LowerColumnBelow`) and affected regions on every level rebuild (`LodManager.MarkEditedColumn`); placements need nothing. All of this runs where the LOD is built (singleplayer and the server): a multiplayer client's far LOD is the server's, streamed as finished vertices, so its edits return before these hooks (see "Multiple players and chat"). Canopy bumps come from `TreeGenerator.TryGetCanopy(x, z, proxy, out top, out leaf)`, read once per fine column with the level's `LodLevelSpec.ProxyCanopy`: the first ring reads the grown canopy of the same cell batches the chunks stamp, and the farther rings read each species' `lod` crown proxy (`LodCrownProxy.TopOffset` over its `LodCrownProfile`), which never grows a tree. Either way a bump wears the leaf block that owns its top cell (the species' `LeavesId`, resolved generically via `BlockType.ById` in `LodRegion.BuildMeshData`, falling back to `TreeGenerator.LeavesBlock`), so a new tree species only needs its species file — never a new LOD branch. An edited canopy reads as open sky: mining or blasting a wood or leaf cell, every fell, every column `LeafDecayManager` clears or `TreeGrowthWriter` writes call `TreeGenerator.PoisonCanopy`, whose `CanopyDisturbed` markers `TryGetCanopy` and `CanopyLeafBlock` consult before either cache. LOD vertices bake a coarse sky exposure from those same column heights into `Vertex.Sun` (`LodSkyExposure`, tuned by the `LodSky*`/`LodValleyShade`/`LodCanopyShade` constants): a vertex darkens by how far the columns in front of or around it rise above it, and a canopy bump darkens toward its base, while open ground, straight walls under open sky and the water sheet keep full sun so the ring matches the near chunks.
